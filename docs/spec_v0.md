# 競合チェッカー（仮称） v0 仕様

［as-of 2026-07-27 | P4実験03 | 状態: **v0実装完了・未デプロイ**（コア＋UI＋全国データ＋全国基準値、テスト20本green）］

名称は仮。v0が答える検索意図は「その場所にその業種の店が多すぎないか」なので、
`競合チェッカー` / `出店密度チェッカー` / `1店舗あたり商圏人口` あたりが候補。ディレクトリ `~/compete_checker/` も仮。

---

## 1. これは何に答えるか

> **半径Rの円内に、その業種の店が人口に対して多いのか少ないのか。全国平均と比べて何倍か。**

商圏メーカーが「そこに誰が住んでいるか（需要）」、ポスティング計算機が「何部刷るか（実行）」に答えるのに対し、
本ツールは「**すでに誰が獲りに来ているか（供給）**」に答える。3本目にして初めて需給の両側が揃う。

対象は既存2本と同じ＝出店検討者・地域集客担当・代理店。

## 2. 調査結果（2026-07-27 実測）— これが設計を決めた

当初案は「Instagram投稿 × Google Maps」だったが、**両方ともv0には入れられない**ことが判明した。

### 2.1 Google Places API：地理院タイルと併用できない

Google Maps Platform 利用規約は Google Maps Core Services（Places / Geocoding 等）の
コンテンツを**非Googleマップ上に表示することを禁じている**（"No Use With Non-Google Maps"）。
既存2本は地理院タイル＋Leafletなので、Places由来の店舗を同じ地図に描いた時点で規約違反になる。

- 地図なしでの表示（一覧・表）はGoogleロゴ等の帰属表示付きで可
- **キャッシュ禁止**（`place_id` のみ無期限保存可）→ 事前に焼いて静的配信する逃げ道がない
- 価格: 評価・レビューを含むフィールドは **$40 / 1,000リクエスト**（Enterprise）。
  月$200クレジット ≒ **月5,000診断で枯れる**。以降は1診断あたり約¥6の変動費

つまりGoogleを入れると「ゼロサーバ・静的・無料」というP4既存資産の性質が3つ同時に壊れる。

### 2.2 Instagram ハッシュタグ検索：生きているが審査ゲートが重い

- `ig_hashtag_search` は健在。ただし **Instagram Public Content Access** という特別機能の承認が必要
- 前提: ビジネス認証・Live modeアプリ・プライバシーポリシー・データ削除経路。**審査2〜4週間、承認は不確実**
- 制約: ユニーク30ハッシュタグ/7日、recentは直近24h、**位置情報は返らない**
- 位置は本文からLLMで店名抽出→ジオコーディングで解決する必要がある（ここがAIネイティブの実体）

**承認が不確実な依存をv0のクリティカルパスに置かない。** IGはv1に隔離する。

### 2.3 代わりに出てきた本命：経済センサスのメッシュ統計

`shoken_maker/docs/roadmap.md` の statsIdプローブ結果（2026-07-24）に、
**500mメッシュの事業所系データ T001153〜156 / T001163〜166**（うちT001154/164が小売細分類）が
すでに実測で記録されている。経済センサス‐活動調査の地域メッシュ統計で、産業別の事業所数・従業者数が入る。

これは既存の `fetch_mesh.py`（`STATS_ID` 環境変数でstatsIdを差し替える設計）でそのまま取れる。
**外部API依存ゼロ・変動費ゼロ・審査ゼロ・地理院タイルのまま**で供給側が手に入る。

## 3. アーキテクチャ判断

**無料側は非Google・完全静的、有料側だけGoogle正規** に分ける。コストが発生する境界と課金の境界を一致させる。

| | 無料（v0） | 有料（v2） |
|---|---|---|
| 供給データ | 経済センサス500mメッシュ（統計値） | Google Places（実在の店名・評価・レビュー） |
| 地図 | 地理院タイル + Leaflet | Googleマップ、または地図なしの表（規約準拠） |
| 配信 | 静的JSON、サーバ計算ゼロ | オンデマンド、1件あたり実費 |
| 粒度 | 「飲食店が32事業所」 | 「A店 3.9★ 412件、B店 …」 |

無料側は**統計として正確だが匿名**、有料側は**個体が見えるが実費がかかる**。
この差がそのまま「無料診断 → 有料成果物」の落差になり、P4の型に一致する。

## 4. v0 スコープ

### 画面（1画面・1クエリ＝円、既存2本と同じ節度）

1. 地図をクリック → 円（半径300m〜5km スライダ）
2. 業種を選ぶ（飲食店 / 小売 / 美容 / 医療 …＝産業中分類ベースのプリセット）
3. 即座に出る:

```
半径 1.0km 圏
  人口          17,432 人
  飲食店         32 事業所（従業者 218 人）
  1店あたり人口   545 人
  全国平均       892 人 → 0.61倍（競合は多め）
  都道府県平均    734 人 → 0.74倍
```

4. URLに状態（`?lat=..&lng=..&r=..&ind=..`）→ そのままシェア可能（既存2本と同じ）

### 計算（純関数・`compete.js`）

- `P` = 円内の常住人口（既存 `mesh.js` の按分ロジックをそのまま流用）
- `E_j` = 円内の業種j事業所数、`W_j` = 同従業者数（同じ按分）
- **1店あたり人口** `P / E_j`
- **需給インデックス** `(P / E_j) / 基準値` — 1未満＝過密、1超＝手薄（境界 0.8 / 1.25）
- **平均店舗規模** `W_j / E_j` — 大型店中心か個人店中心かの判別
- `E_j = 0` のときは1店あたり人口も需給インデックスも **null**。
  「店が無い＝無限に手薄」とはしない（人口0の山中と人口1万の空白地帯を混同しないため）
- 全国・都道府県の基準値はビルド時に前計算して定数化

### 分母は「昼間人口の代理」を主にする（2026-07-27 実装中に判明）

常住（夜間）人口だけを分母にすると、繁華街・オフィス街で数字が壊れる。実測:

| 地点（半径1km） | 常住人口 | 全産業従業者 | 飲食店 | 1店/夜間 | **1店/昼間代理** |
|---|---|---|---|---|---|
| 新宿駅 | 24,300 | 384,455 | 2,367 | **10** | **173** |
| 自由が丘駅 | 52,984 | 24,014 | 385 | 138 | 200 |
| 武蔵小杉駅 | 74,014 | 47,884 | 416 | 178 | **293** |
| 奥多摩（山中） | 958 | 828 | 8 | 120 | 223 |

夜間人口だと新宿が「10人に1店」という無意味な値になり、奥多摩(120)が自由が丘(138)より
過密に見えてしまう。**昼間人口の代理 = 常住人口 + 全産業従業者数** に替えると、
順序が実感どおり（新宿が最も過密、武蔵小杉が最も余裕）になり、桁も揃う。

全産業従業者数は **T001163 に既に入っており追加取得は不要**。

**ただしこれは代理指標であって昼間人口そのものではない。** UIに明記する:
- 同じセルに住み、かつ働く人を二重に数える
- 就業も通学もしない来街者（買い物客・観光客）を含まない

正確な昼間人口は国勢調査の従業地・通学地集計（1kmメッシュ）にあり、
`shoken_maker/docs/roadmap.md` が「最重要級」としている将来レイヤー。v0では代理で足りる。

UIは**夜間ベースと昼間代理ベースの両方を出す**（`summary()` が両方返す）。
片方だけ見せると必ず誤読されるので、並記が正しい。

### 第2画面（v0.5・静的のまま可能）

全国の各500mメッシュについて需給インデックスを前計算してヒートマップ表示。
「**人はいるのに店がない座標**」が地図上で光る＝当初案②の空白地帯マップが、Google抜きで成立する。

## 6. 精度と免責（UIに明記する）

- **事業所 ≠ 店舗**。本社・事務所・無店舗事業所を含む。飲食店など対面業種では概ね店舗に近いが、業種により乖離する
- 調査年次は経済センサス（2021年6月1日時点、5年周期）。**直近の開店・閉店は反映されない**
- 人口は常住（夜間）人口。昼間人口ではない（商圏メーカーと同じ注記）
- 人口は2020年10月1日、事業所は2021年6月1日と**基準日が8か月ずれる**

### 秘匿の実測（2026-07-27・T001163 メッシュ5339=東京圏 16,594セル）

**秘匿は実質存在しない。中分類は500mメッシュでそのまま使える。**

- 非数値トークン（`*` 等の秘匿記号）の出現 **0件**
- 事業所数が **1件だけのセルもそのまま公開**（飲食店で2,719セル＝非ゼロセルの27%）
- 従業者数も秘匿されていない。事業所1件のセルでも平均7.5人が入っており、
  従業者0のセルは5件（0.2%）のみ＝秘匿ではなく実態（従業者を伴わない事業所）と解するのが自然

| 業種 | 合計(5339圏) | 非ゼロセル | 1セル中央値 |
|---|---|---|---|
| Ａ～Ｓ全産業 | 1,124,457 | 100.0% | 31 |
| Ｍ76飲食店 | 111,341 | 60.9% | 3 |
| Ｎ78洗濯・理容・美容・浴場業 | 58,537 | 58.0% | 3 |
| Ｐ83医療業 | 60,072 | 56.0% | 3 |
| Ｏ82その他の教育，学習支援業 | 34,976 | 51.7% | 2 |

半径1km（≒12.6セル）なら飲食店は数十件規模になり、指標として十分な分解能がある。
半径300mだと1〜3セルで中央値3件のため、**小半径では分母が小さくなる旨をUIに注記する**。

## 8. 計測設計（2026-07-27 実測にもとづき全面改訂）

### 現状の実測

| 層 | 状態 |
|---|---|
| 流入（参照元・ページ） | Vercel Web Analytics で収集中（ダッシュボード側で有効化・repoに痕跡なし） |
| 申告（S4フォーム3本） | **回答0件**（2026-07-27時点。公開2〜3日目のため母数不足か設計かは未分離） |
| **クエリの中身（座標・半径・業種）** | **未収集**。`history.replaceState` でURLに書くだけでどこにも残らない |

### 発見した設計欠陥（既存2本）

S4フォームは `業種[必須] / エリア[必須] / メールアドレス[必須]` の順で、
**最も価値ある情報（業種×エリア＝何をどこに出そうとしているか）を、最も摩擦の高いメール必須の壁の向こうに置いている**。
通過するのは「すでに相談する覚悟がある人」だけ＝無料ツールの独自価値である
「**まだ誰にも相談していない段階の検討**」を構造的に取りこぼす。

### 原則（株主決定 2026-07-27）

> **収集は「聞く」のではなく「観測する」。** 憲法の「聞く前に測る、測れないものだけ聞く」をユーザーにも適用する。
> 業種は測れる（ツールの入力として自然に出る）から聞かない。メールは測れないから聞く。
> フォームは測れないものだけに使う。

系として:

1. **業種はツール本体の必須入力にする**。競合マップは機能上そうなるので自動的に成立する。
   商圏メーカーにも業種を足せるが、計測のためでなく**ユーザーの利益として**
   （例: 飲食店を選ぶと昼間人口の注記が出る）＝入力する理由を本人側に作る
2. **メールは最後に任意で置く**。フォームから業種・エリアの必須を外す
3. **入力の瞬間に意識させない ≠ 隠す**。母数を減らすのは入力要求であって開示ではないので、開示は必ず行う

### 実装（cookieless・同意バナー不要）

- 端末に**何も書かない**。クエリは自前エンドポイント（案: Cloudflare Workers + D1）へPOST
- セッションの束ねはサーバ側で `hash(IP + UA + 時間窓)`。**生IPは保存しない**
- 同意バナーは要らない＝「意識させない」を最大化する形が、そのまま法的にも安全側になる
- 記録は**出来事のみ** `{ts, sid_hash, tool, event, payload}` の append-only。
  「このエリアは人気」等の状態は書かず、使う時に導出する（憲法通り）

### 結合しない原則

**メールアドレス（フォーム側）とクエリログを結合しない。**
結合した瞬間にログ全体が個人データになり、将来の第三者提供（不動産・FC本部等）で同意問題が発生する。
分離は制約ではなく、**売れる形を保つための設計**。

### 価値が出る条件

- 単発のクエリは薄い。価値は**系列**にある（半径を絞った／業種を変えた／2地点を比較した＝迷いと収束）
- 最も価値が高いのは**収束点＝セッション最後に見た地点**。途中の探索と区別できる形で記録する
- 集計が記事（「月次・出店検討が多かったエリアTOP50」）になる件数の閾値は未測定。
  計測レイヤ投入前に予測として `predictions.jsonl` に書いてから測る

## 9. 「店名リスト」をどこから出すか（2026-07-27 追記）

個店名の一覧は**出所を3つに割る**。同じリストを1つの源から作ろうとすると必ず規約か費用で詰まる。

| 出所 | 得られるもの | 再配布/キャッシュ | 地図 | SEO面に載るか |
|---|---|---|---|---|
| **食品衛生申請等システム**（厚労省オープンデータ） | 店名・所在地・業種・**許可日** | **可**（要規約確認） | 地理院タイルのまま | **生成できる** |
| Google Places | 評価・レビュー数・写真・営業時間 | **不可**（place_idのみ） | Googleマップ or 地図なし | **原理的に不可** |
| Instagram ハッシュタグ | 「語られている店」＝話題の部分集合 | 可（投稿本文） | 制約なし | 生成できる |

### Googleが流入装置になれない理由（決定的）

キャッシュ禁止 ⇒ データを保存できない ⇒ **静的ページを生成できない** ⇒
商圏メーカーの `gen_pages.py` 相当のロングテールLLMO面が**Googleデータでは作れない**。
Googleは「LLM流入→無料診断」の流入側には載せられず、**変換後（有料レポート）専用の部品**として扱う。

### 食品衛生オープンデータ（v1の本命）

- 毎月15日更新・前月末時点、自治体別CSV（`https://ifas.mhlw.go.jp/`）
- **許可日が入る**＝「このエリアで今年何軒開いたか」という開店の時系列が出せる。
  Google/OSMのどちらにもない軸で、出店検討者には評価より効く可能性がある
- 弱点: ①**2021年6月以降の許可・届出のみ** ②閉店の反映が弱い ③住所文字列のジオコーディングが必要
  （地理院ジオコーダで無料・規約適合）
- **網羅率の仮説**: 飲食店営業許可は5〜6年更新。2021年6月から5年経った2026年時点では
  既存店もほぼ一巡して載っているはず。**検品方法は v0 が与える**——
  `許可データ件数 ÷ 経済センサスの飲食店事業所数` を自治体別に出せば網羅率がそのまま測れる

OSM Overpassは中間（無料・再配布可だが網羅性が読めない）。上記2つで足りるなら不要。

## 11. 却下した案と理由

- **保存したIG投稿→行きたい地図（B2C）**: データ扉（エクスポートZIP）にURLしか入っておらず復元コスト大。
  消費者課金も弱い。流入装置としてのみ将来検討
- **OSM Overpassで店舗を引く**: 経済センサスが統計的に完全な事業所数を無料で与えるため、v0では不要。
  実店舗名が要るv2ではGoogle Placesの方が精度が高い
- **商圏メーカーのレイヤーとして実装**: ロードマップ上は同一レイヤーだが、有料化と変動費を
  ゼロサーバ原則の商圏メーカーに持ち込みたくない。検索意図も別なので独立ツールとする
